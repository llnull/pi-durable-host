Pi Durable 分析报告

一个为「长时运行、可持久恢复、可任意部署、随时可塑」的 Agent 而生的 Harness 运行时 —— 结合官方博客与本地 host 实现的分析。

报告日期 2026-10-08 @earendil-works/pi-durable v1.1.0（实验性） Node v24.13.0 本地路径 ~/vibe-ws/pi-durable 依据：官方 Blog + 库 README + 本地实现与数据实证

01摘要（TL;DR）

Pi Durable 是什么：它是 Earendil 随 Pi 1.0 一同发布的实验性 npm 包（@earendil-works/pi-durable），一个「持久化 Agent Harness」运行时库。官方博客的定位一句话："built specifically for long-running, durable, and malleable agents that can run anywhere"（专为能随时随地运行的长时、持久、可塑 Agent 而造）。

  • 它不是 Pi 编码代理的替代品，也不是一个开箱即用的 CLI/服务，而是一个框架/库：你用它来构建任何 Agentic 应用（Slack bot、工单分诊、值守 Agent、 coding agent 都可以）。
  • 核心主张：会话（transcript）、模型轮次、工具调用、应用状态，一切先原子提交到存储、再呈现。进程在任何时刻死掉，下一个打开同一存储的进程都能从上次的检查点继续。
  • 三个基座：模型访问用 pi-ai（与本座 Pi CLI 共享），文档状态用 chord，自身约 1.5 万行 TS 源码（不含测试），刻意保持极简与可塑。
  • 本地实践：当前目录就是一个最小可用的本地 host（host.js）：SQLite 存储 + Ark relay 模型 + CodingTools（read/write/edit/bash）。已实测跑通模型往返、工具链、跨进程持久化、以及 kill -9 崩溃后自动续跑（被中断的非幂等工具按约定向模型报 interrupted，模型自行改用后台执行完成任务）。
  • 一句话理解：把「Agentic loop」从一次性进程，升级为随时可断、可续、可接管、可多端观察和操纵的持久状态机。
⚠ 实验性声明

官方明确标注 API 随版本变动（1.1.0 就包含 breaking change：Storage 需支持 order 字段、TaskRuntime.context() 签名调整）。生产使用需锁定版本并关注 CHANGELOG。

02背景：Pi 生态与「Harness」概念

2.1 Pi 1.0 与 Earendil 的意图

Pi 1.0 是一个硬化过的、极简的、可扩展的终端编码代理 Harness，面向「一个人、一台（远程）机器、一个终端」的场景：进程死了，人看一眼现场，然后让它继续。Earendil 在 Pi 1.0 博客中直言，很多人想用 Pi 的方式不止于终端和编码——他们需要可以从不同界面触达、支持更长时间运行的对话与任务。"In short, Pi must become more durable." 但他们不愿破坏 Pi 的极简，于是把这些探索收进一个新包：Pi Durable。

  • Pi Durable 不替代 Pi 编码代理；它与 Pi 共享代码（如 pi-ai）与原则（minimalism、malleability）。
  • 它是构建任意 Agentic 应用的框架，同时也是设计试验田：在 Pi Durable 上验证过的设计，将来会反哺 Pi 编码代理。

2.2 什么是 Harness（官方定义）

📖 官方博客对 harness 的定义
"A harness is storage plus the machinery needed to run one or more conversations with large language models in parallel. It provides the tools those models call, and the execution environments the tools run in."

拆开看，一个 harness 由四类角色构成：

角色含义
Conversation你与 agent 的交互，记录为一份 transcript（不可变条目序列）。
AgentLLM + 其设置（thinking 等级、可用工具、指令、工作目录）。
Tool / Execution Env工具是模型可调用的能力；工具通过执行环境干活——可以是你的笔记本、远程 VM、内存沙箱。每个会话可以有自己的工具集与环境。
TaskHarness 运行的一切——从「调模型」到「执行工具」——都是任务（task）。

另一个有意思的细节（体现 Pi 系的哲学）：Pi Durable 的源码被刻意控制在约 15,000 行（不含测试），官方说这是为了让 agent 自己也能读懂它——约 15 万 tokens（GPT 计）到 25 万 tokens（Claude 计），而构建应用时通常只需要其中一部分（如 3,000 行的存储后端可以跳过）。

03目的与设计目标

博客用一组 "We want …" 阐明了设计目标，每一条都对应一个具体机制。这张对照表是理解整个系统的钥匙：

设计目标（We want…）Pi Durable 的机制
① 长时运行、随处运行
Long runs anywhere		Harness 打开在存储后端之上（memory / SQLite / JSONL / Cloudflare Durable Object）；可移植核心不用 Node API，小适配即可跑在 Bun / DO；存储接口很小，可自己实现到 KV、Postgres 上。SQLite 模式下只把工作集放内存，配合 compaction，几万条消息的会话也能装下。工具通过执行环境接口拿文件和 shell——harness 在 A 机、工具在 B 机完全可行。
② 崩溃存活
Survives crashes		run 的每一步都是带检查点的任务；进程死后新进程发现未完成任务并从上个检查点继续。被切断的模型请求会重发（部分答案保留并标记 aborted）；被切断的工具调用仅在声明 replay: "safe" 时重跑，否则向模型报 interrupted；requestId 让提交恰好一次；排队中的消息仍在队列。
③ 多会话并发
Many conversations at once		一个 harness 同时跑任意多个会话互不阻塞；会话可在 transcript 任意点 fork（不复制历史，引用父历史前缀）；每个会话存自己的 agent 配置（模型/工具/目录/指令）——博客给了 Slack 频道 + 线程的例子。
④ 一切可插拔且参与持久化
Extensions		Extension = 具名打包的 system prompt sections + tools + hooks + wraps + tasks。会话只存扩展名字；工具调用本身也是持久任务（intent 先落库）；hook 可拦截/改写请求与工具调用，决策可存 memo 保证崩溃后不重问；扩展自带任务享受同一套检查点机制。
⑤ 无限长对话
Compaction		compaction 是一个普通任务，边聊边压缩：接近上下文上限时后台生成摘要，下一个回合边界落位；provider 拒绝超长时自动压缩并重试一次；也可手动压缩/带指令压缩；reset() 与 control:{handoff} 支持交接式重启，旧内容永不删除、仍可检索。
⑥ 应用状态同样持久
Durable application state		todo、plan、工单、沙箱选择等应用状态放 Documents：与 transcript 同一原子提交修改的带类型 JSON，fork 策略可选（继承 fork 点的值 / 当前值 / 全新）。
⑦ 运行中的代理可改代码
Malleable		Registry 支持热替换同名扩展；正在跑的调用用旧代码跑完，下一次调用用新代码；会话只存名字不存代码，重启后自动接上新进程安装的版本。
⑧ 多人/多端协作
Multiplayer		UI 需要的一切都是已提交状态：任意数量客户端可 attach 任意会话，先拿当前视图、之后只收增量；迟加入/重连从当前视图开始；任何客户端都可以 steer 运行中的会话或排队跟进。
💡 一句话归纳

Pi Durable 把「harness = 存储 + 跑会话的机器」这个定义推到极致：存储是唯一事实源（single source of truth），进程只是随时可死可生的「工人」——工人死了，事实还在，新工人接着干。

04核心概念模型

4.1 术语表

概念说明
Harness一个打开的存储 + 运行 agent 的全部机器。所有变更走同一条原子提交路径，任何东西先落库再呈现。
Conversation一份 transcript（不可变条目的树）。root() 首次使用时创建、之后每次重启拿到的是同一个；句柄无状态，按 id 比较。
Entry一条不可变记录：用户消息 pi.user、模型响应 pi.assistant、工具结果 pi.tool-result、系统提示变更 pi.system、重置 pi.reset、压缩 pi.compaction、以及自定义 kind。模型只看到最近一次 reset 之后的条目。
Commit原子写。一次 commit 可同时追加 entries、改 documents、建 tasks——要么全部落库要么全不落。
Document存在 transcript 旁边的带类型 JSON 状态。内置五种：pi.agent（会话的 agent 选择）、pi.provider（面向 provider 的会话身份，UUIDv7）、pi.live（正在跑的生成与工具）、pi.inbox（排队提交）、pi.usage（花费）。可用 defineDoc 自定义。
Task持久状态机：每一步先存 checkpoint 再继续；重启后从上个 checkpoint 接着跑。每个任务有 owner（会话或另一个任务）。
Submission交给会话的东西（用户输入或要写入的 entry），可等待其结果（done / unanswered+reason）。
Turn / Runturn = 一次模型响应及其工具调用；run = 从一个输入到最终答案的全部 turns。run 进行中会话是 busy 的。
Extension / Registry具名的 sections/tools/hooks/wraps/tasks 打包；Registry 是本进程安装的扩展集合，运行时可变。
Agent（配置）会话运行的一切选择：model、thinkingLevel、extensions、tools、instructions、cwd——按名字存于 pi.agent，每次使用时对 Registry 解析。
Execution Env工具真正干活的地方（env 函数按会话 cwd 构造）。接口小：读文件、列目录、跑程序、watch。

4.2 一次 run 的生命周期（内置任务的编排）

submit({ type:"input", content })原子提交 → transcript 追加 pi.user；返回 Submission
▼
内置任务 pi.generation 启动按所选扩展渲染 system prompt；只有变化的部分才重发（保 prompt cache）
▼
system 变更记为 pi.system（仅在变化时）→ 模型响应落库为 pi.assistantthinking / text / toolCall 均为消息内容块
▼
有工具调用？→ 每个调用一个 pi.tool 任务intent 先提交，再 execute；结果落库为 pi.tool-result（generation 拥有这些任务并等待它们）
▼
pi.generation 继续：带上工具结果再次请求模型循环，直到模型给出不含工具调用的最终回答
▼
submission done（或 unanswered + reason）host 可再把 AssistantEntry 提交进 transcript

4.3 所有权树（Tasks + Conversations）

  • 任务与会话构成一棵所有权树：子代理（subagent）是「被某个工具调用任务拥有的会话」；支付任务是「被 checkout 任务拥有的任务」。
  • 中止自底向上：中止一个任务先中止它拥有的东西，每个任务先清理自己的影响（如退款），父任务的全部工作完成后才算 idle。
  • 前台 vs 后台：前台任务属于会话「当前工作」（Esc 会中止它们）；background: true 的任务是边界——会话在它运行时照样 idle，普通中止碰不到它（适合「活得比本轮久」的子代理、明天的提醒）。abort(context, { background: true }) 才能停掉它。
  • 内置 pi.generation 正是这套机制的示范：它调用模型、为自己的每次工具调用创建 pi.tool 子任务、等待、再进入下一轮。

05关键机制详解

5.1 持久化与崩溃恢复 —— 这个库的灵魂

  • 先提交、再行动：工具调用的 intent 在 execute() 之前就落库；流式部分答案与工具输出默认至多每 100ms 提交一次——崩溃最多丢这个窗口的内容。
  • resume：harness.resume() 启动任务调度器，接续上个进程留下的未完成任务（submit/wait 也会隐式启动）。模型请求被切断 → 重发，部分答案保留并标记 aborted。
  • replay 语义（二选一）：
    • replay: "safe"（只读类工具）：崩溃后重跑该调用；配合 requestId/所有权索引，重跑能「找到同一个子代理/同一笔支付」而不是重复创建。
    • 未声明 safe（副作用类，如 deploy）：不重跑。模型收到 interrupted 错误结果 + 已落库的部分输出，由模型自己决定下一步。
  • 幂等提交：同一 requestId 的重试返回已存在的 submission，客户端崩溃重连也不会把同一个问题问两遍。
  • 会话身份持久化：每个会话有持久 UUIDv7（pi.provider），作为 sessionId 转发给 pi-ai，用于 provider 的 prompt cache 亲和；跨重启/重试/压缩/换模型保持不变。
  • 排队语义（busy 会话）：会话忙时，新提交进 inbox：follow-up（默认，答完后排）、steer（插入当前工具轮之后、并入正在跑的工作）、reject（忙时直接抛错）、以及不问模型的 write。run 失败时队列保留，下次提交按序放置。
✅ 本地实证（对应 7.4 节证据链）

本地已验证：kill -9 打断一个 25 秒的 bash 调用 → 重新打开存储自动续跑 → 模型收到 "[error] Tool bash was interrupted and may have partially run" → 模型自主改用后台执行 + 轮询 → 任务完成，最终答案正确。这正是上面 replay 语义的活教材。

5.2 存储后端

后端导入说明
MemoryMemoryStorage（包根）不持久化，测试用。
SQLiteopenNodeSqliteStorage(file)单数据库文件；WAL + synchronous=NORMAL：进程崩溃不丢已提交数据；断电/宿主机故障可能丢最新提交。（本地 host 即此模式）
JSONLopenNodeJsonlStorage(dir)目录内只追加文件；可 { fsync: true } 每次提交前刷盘。
Cloudflare DOopenDurableObjectSqliteStorage(ctx.storage)跑在 Durable Object 的 SQLite 上，commit 即其存储事务。
  • SQLite/JSONL 的可移植核心不含 Node API——给一个异步 SqliteDatabase 门面或 FileSystem 就能跑在 Bun / DO 上；存储接口小（exec/run/get/all/transaction/close），官方提供一致性测试套件（registerStorageConformance）与 benchmark 供自研后端（KV/Postgres）验收。
  • 单写者模型：一个存储同一时刻只能被一个进程打开，没有跨进程锁——其他客户端应 attach 到持有进程（见 5.7）。这是部署时最容易踩的坑。
  • 内存占用策略：只保留工作集（活跃 transcript、活任务、待定 submission），活跃 transcript 天然被 compaction 限制在上下文窗口量级。

5.3 无限长对话：Compaction / Reset / Handoff

  • compaction 是一个普通任务：压缩期间会话继续干活；摘要放 pi.compaction 条目（含摘要 + 指向保留的第一条目），老条目永远留在存储里。
  • 自动压缩（settings.compaction）：backgroundTokens 之下先在后台起压缩；超过 contextWindow - reserveTokens 时下一请求等压缩完成；provider 拒超长 → 压缩 + 重试一次。keepRecentTokens 控制近端逐字保留量。
  • 手动压缩：root.compact("保留失败测试名", ctx)，可带指令；Esc 可取消。
  • reset / handoff：reset(note) 开新上下文（可选交接便签）；工具返回 control: { handoff: "..." } 可在运行中触发同样效果——博客演示的「自我交接 agent」：handoff 工具重开上下文 + search_history 工具照常检索被交接掉的历史。
  • 多个压缩在途时，切得最深的那个生效（浅的结算为 stale）；beforeCompact hook 可拒绝或自供摘要。

5.4 多会话 / Fork / 子代理

  • fork：root.fork(entryId, …) 从任意条目分叉——子会话看到父历史前缀但不复制，独立继续；继承分叉点的 agent 配置，但拿新的 provider 会话身份（不污染父的 prompt cache）。
  • 每个会话自己的 agent：模型、thinking、扩展与工具、额外指令、执行目录。博客场景：主编码 agent 旁挂一个 reviewer——更便宜的模型 + 只读工具 + 自己的 checkout。configure() 一次提交改完，未设字段跟随 host 默认，null 清回默认。
  • 子代理 = 几行代码的模式（不是内置功能，这是刻意的极简）：
    1. 工具内 api.commit 创建 ownership: { kind:"task", taskId: api.taskId } 的会话（先查所有权索引避免重复创建）→ 声明 replay: "safe"，崩溃重跑找到同一个孩子；
    2. api.details({ conversationId }) 让 UI 能把子会话挂在调用下面展示；
    3. submit + wait，答案从子会话 transcript 读回。
    中止该调用即中止孩子；调用失败/崩溃同样；父会话要等孩子 idle 才算 idle。官方示例覆盖前台子代理（22）与持久后台子代理（23：spawn/steer/stop/list，回复以 follow-up 送回，requestId 防重复上报）。

5.5 扩展系统：sections / tools / hooks / tasks

  • Sections（system prompt）：每次请求前由所选扩展重新渲染；变更以位置化 system entry 记入 transcript（重启/fork 看到的与模型当时看到的一致）；支持中途 system/tool 变更的 provider（如 Anthropic）只重发变化部分，prompt cache 保持热。注意：每次返回不同内容的 section（如当前时间）会废掉缓存。
  • Tools：TypeBox schema 定义参数，harness 先验证再执行；api.output() 流式输出；同名工具后者覆盖前者（如 venv 版 bash），wrapTool 装饰胜出者（如计时）；工具还能返回 control:{ terminate }（整轮都要求则结束 run）或 usage（计入会话花费）。
  • Hooks（链式）：beforeTool（改参/阻断，链式传递改参，第一个 block 生效，抛错=阻断）、afterTool（替换结果）、beforeRequest（替换一次请求的消息）、afterResponse（观察）、onYield（让 run 继续跑，如「再干一会儿」）、afterTools。hook 崩溃后会重跑 → 决策存 memo（首次写入胜出），如「deploy 审批」问过一次就不再问。
  • 自定义任务：defineTask 带版本、phases、checkpoint、等待其他任务（waiting + allSettled/failFast）、abort 处理器（退款式清理）。博客的 checkout/payment 示例展示了幂等扣款 + failFast + 崩溃重启全流程。
  • 环境感知：env 函数按会话 cwd 为每次调用构造环境 → 每会话一个目录/容器；自定义 ExecutionEnv 用 id 标识「同 id 同文件同路径」，可注册一致性测试验证。

5.6 可塑性（Malleable）：运行中热更新

  • registry.install(ext) 同名即原地替换；registry.uninstall 移除。会话存的是名字——扩展卸载后相关会话只是暂时拿不到它，重装即恢复。
  • 变更边界清晰：已在跑的工具调用用旧代码跑完；每个任务 phase 开始时解析一次 hooks/agent；下一次请求/调用用新代码。重启后重装同名扩展即可，未完成的扩展任务等它装回来再恢复。

5.7 多端协作：viewState / watch / watchEvents

  • 一切 UI 需要的都是已提交状态——这是 Multiplayer 的前提。三个层次：
    API用途
    viewState()会话结构视图（只读 Chord state，每次提交后更新）：entries、pi.live（流式部分答案/重试/工具输出）、pi.inbox、pi.usage、pi.agent、pi.provider。
    watch()同一视图 + 每次 commit 的精确操作序列，小到能走 socket——远程客户端方案。
    watchEvents()转成编码代理风格的事件流（message_start / tool_execution_start…，带增量 delta），字节更多但熟悉；落后超 100 批 → 收到全量 snapshot。
  • 迟加入/重连从当前视图开始（不回放历史）；落后时最多保留 100 帧然后折叠为最新全量帧。
  • 任何客户端都能 submit({ whenBusy: "steer" }) 中途转向运行中的会话（博客场景：Slack 里有人插话「先查 staging 日志」）。
  • 另有 harness.taskGraph() / watchTaskGraph()：全 Session 活任务树（owner 边、状态、background 标记、拥有的会话），适合做任务面板/调试。

5.8 应用状态：defineDoc

  • defineDoc({ kind, version, scope, history, fork, initial })：与 transcript 同一原子提交修改的带类型 JSON——应用状态（todo/plan/工单/沙箱映射）与产生它的对话永远一致。
  • history: "latest" | "rewindable"（可回读旧值）；fork: "initial" | "current" | "asOf"（fork 从哪个时点继承）。
  • UI 订阅：harness.documentState(Todos, id) / watchDoc()；扩展的 sections/tools 可通过 input.read / api 读自己的文档。
  • HarnessOptions.conversationCreated 钩子保证每个新建/fork 的会话（含工具里裸创建的）都带上你的文档。

host.js 是「Pi Durable 最小宿主」的范本，五个构建函数 + 四个命令：

函数/命令做什么 · 关键点

getRoot()harness.root(ctx, { agent: { model, thinkingLevel:"high", cwd, instructions } })。注意：agent 参数只在首次创建会话时生效；此后配置存于 pi.agent 文档——所以换了目录要跑 config 命令同步。

history [n]root.entries({}, n) 取最新 n 条（新→旧翻转），按 kind 打印（pi.user / pi.assistant / pi.tool-result / pi.system）。

configroot.configure({ cwd, model }) 把存储的 agent cwd/model 重置为本目录当前值（目录迁移后跑一次）。
ℹ 每个调用都带 Context

所有异步调用都传入 Chord Context（host 用 BACKGROUND_CONTEXT，永不取消）。取消一个 wait 只取消等待本身，从不取消工作——这是「观察与执行分离」在 API 层的体现。

验证项结果 · 证据

② 工具链write → read；workspace/hello.txt 落盘，内容 hello durable。

崩溃恢复证据链（kill -9 实验，条目号取自 entries 表）

提交任务entry 20 · pi.user

host.js ask "运行命令 sleep 25 && echo finished-25s，然后报告输出"。

generation 启动，模型调用 bashpi.tool 任务

工具 intent 已落库，execute() 正在跑一个 25 秒的命令。

host 进程被 kill -9

bash 工具未声明 replay-safe → 不会重跑；run 中断保持 pending 状态躺在 SQLite 里。

重新打开存储，resume() 接续

generation 恢复；模型收到被中断工具的结果：isError: true，正文 [error] Tool bash was interrupted and may have partially run，诊断码 interrupted。entry 25 · pi.tool-result

模型自主决策entry 27 · pi.assistant(thinking)

thinking 原文大意："The bash tool was interrupted and may have partially run… 输出丢了，改用后台执行 + 轮询文件更稳妥。" —— 恢复语义不是框架硬修，而是把事实交给模型。

后台执行 + 轮询entries 29/33 · pi.tool-result

后台启动拿到 pid；轮询读到 finished-25s；workspace/out25.txt 留存（13 字节）。

任务完成entry 35 · 最终回答

"命令已执行完成，输出内容为：finished-25s（首次直接运行被中断后改用后台方式执行，从 out25.txt 确认了该输出）。"

✅ 这个实验证明了什么

进程死亡没有丢失任何已提交事实；未完成的 run 被下一个进程自动接续；副作用类工具的中断按约定不盲目重放，而是让模型拿到「interrupted + 已有输出」后自行补救——这正是博客 "Survives crashes" 一节的全部承诺。

7.5 已知限制（本地 README 记录 + 实测）

  • 费用统计偏低：relay 只回传 cacheRead，cacheWrite 恒为 0，模型 cost 全填 0 —— pi.usage 只可看 token 不可看钱。
  • 单进程拥有存储：无跨进程锁——同一时刻只能有一个 host 进程打开 session.sqlite。多次 ask 串行跑没事，并发跑两个 host.js 会冲突（见第 9 节）。
  • agent 配置在存储里：root() 的 agent 参数只首次生效；目录迁移后需 host.js config 同步（cwd/model 存在 pi.agent）。
  • 非服务形态：无常驻进程/systemd/远程接入配置；Codemode 与此项目无关。它是「库形态」的第二套运行时。
  • 平台性能：data/ 在 Windows drvfs 上，SQLite WAL 可用但慢于 ext4。
  • node:sqlite 实验警告：Node ≥22.19 的内置 SQLite 尚为 Experimental，警告可忽略。

09风险与注意事项

风险说明 · 缓解
实验性 API 变动官方声明 "API changes without notice between releases"；1.1.0（2026-10-07）即含两处 breaking change。缓解：锁定精确版本，升级前读 CHANGELOG。
单写者模型存储无跨进程锁；两个进程同时打开同一 SQLite = 数据竞争/报错。缓解：host 外包一层 flock；或收敛为单一常驻进程 + 客户端 attach。
持久化语义边界SQLite WAL + synchronous=NORMAL：进程崩溃安全，断电/宿主机故障可能丢最新提交；流式进度默认 100ms 一提交。需要更强保证 → JSONL fsync:true 或调大 progress 间隔换吞吐。
prompt cache 失效陷阱每次渲染都变的 section（时间戳等）会废掉 prompt cache；改动频繁的扩展影响成本。缓解：让 section 输出稳定，或接受代价。
replay 划分是安全边界把副作用工具（deploy/付款/发消息）标成 replay-safe 会造成崩溃后重复执行。缓解：默认不标；用 requestId + 所有权索引做幂等。
费用观测盲区本地 relay 场景 cacheWrite/cost 缺失，pi.usage 的金额维度失真（token 维度仍有效）。
平台性能drvfs 上的 SQLite 慢；重负载把 data/ 移回 ext4（Linux 原生路径）。

10演进建议

短期（现有 host.js 上加几行）

  • 幂等化 ask：给 submit 传 requestId（如日期+内容 hash），脚本/定时任务重复调用零风险。
  • 单进程保护：启动时对 data/ 加 flock（或先探测 -wal 活跃），把「一个存储一个进程」从纪律变成机制。
  • 自动压缩上线：host 默认 settings 里开 compaction（reserveTokens/backgroundTokens），为长会话做准备——当前 27 条 entry 还远未触及，但机制值得先开。
  • wait 命令常态化：开机/部署后先跑 host.js wait，把「接续上个进程」变成运维惯例。

中期（长成一个小服务）

  • 常驻进程 + 多端观察：把 host 改成 daemon，暴露 watchEvents()（编码代理风格事件）或 watch()（紧凑 ops）给一个简易 web UI；多人在 UI 里 steer/追问。
  • 自建扩展：项目上下文 section（读 AGENTS.md/技能目录）、危险命令审批 hook（beforeTool + memo 存决策）、计时 wrap 等——都只是 defineExtension 的事。
  • 子代理/后台任务：用 README 22/23 号示例的模式给重活开后台，Esc 不误伤；会话级 taskGraph 做个任务面板。
  • 环境隔离：把 ExecutionEnv 换成 per-conversation 容器（实现接口即可），harness 与工具执行解耦。

长期（生态位展开）

  • 存储升级：多机/云上把 SQLite 换成 Postgres/KV 后端（conformance 套件保正确性）。
  • Serverless 部署：Cloudflare Durable Objects 上的 PiHarness beta——存储、计算、多端接入同一对象内闭环。
  • 典型应用落地：博客预告的 Slack bot / GitHub triage bot 形态：fork 做线程、steer 做插话、handoff + search_history 做「永远在线的长期记忆」agent。
